# KM0 设计文档

KM0 是编码 Agent 的上游：把一句任务描述变成谈清楚的需求、定好的方案，以及每个任务该交给哪个 Agent、用哪个档位的模型，再打包交接给下游执行。名字取自“零公里”，所有道路的里程都从这里起算。

本文档是改造规划的仓库版本，随实现推进更新。

## 定位与目标

要解决的问题：

- 编码前需求和选型没谈清，Agent 边写边猜，返工多。
- 所有任务都用最贵的模型，成本高；全用便宜模型，复杂任务又容易失败。
- 换一个 Agent 接手时，上下文要手工整理。

第一期不做的事：

- 不执行代码、不修改目标仓库、不安装依赖，对仓库始终只读。
- 不做请求级的模型代理（那是 Claude Code Router 这类工具的层，KM0 可以作为它的上游）。
- 不做通用研究报告和评测框架。

成功标准：

- 小任务从输入到拿到交接包，不超过 2 次交互。
- 完整通道每个讨论阶段不超过 3 轮、每轮不超过 3 题，全程只点“推荐”也能走完。
- 每个任务都有 Agent 和模型、预计通过率、期望成本和理由，并且可以手动覆盖。
- 给出与“全部用最强组合”相比的成本对比。
- 交接包粘贴到 7 种目标 Agent 中可以直接开工。

## 核心流程

```
输入任务描述（可附本地仓库路径）
      │
  任务分诊（路由模型）
      ├─ 快速通道：小改动、明确的修复 → 最多 1 个确认问题 → 任务卡
      ├─ 轻量通道：中等功能 → 1–2 轮合并提问 → 精简版文档
      └─ 完整通道：新项目、大功能 → A 定位与规模 → B 产品需求 → C 技术选型 → D 实现方案 → PRD + 技术方案
      │
  任务拆解与路由：档位 · Agent · 成本
      │
  交接包：7 种 Agent 格式，复制或下载
```

用户可以随时手动改通道。完整通道中回改任一决策，只有受影响的阶段需要重新讨论。

## 提问机制与决策账本

讨论分三层：阶段、轮次、问题。每道题绑定一个决策键，回答直接写入决策账本，文档只从账本生成。AI 推断或代为决定的值不能超出已有决策，例如不能给用户没选的功能安排模块。产品需求阶段，如果产品要打分、排序、定价、审批或有状态流转，优先把 `core_rules` 作为那一道可选题来问。

| 阶段 | 决策键（必填 / 可选） | 典型问题 | 默认值来源 |
| --- | --- | --- | --- |
| A 定位与规模 | 必填 `scale`、`user_scale`；可选 `compliance`、`timeline` | 交付形态（本地工具 / 开源项目 / 在线部署 / 企业级）、用户量、合规、时间预算 | 任务描述；已有仓库的特征 |
| B 产品需求 | 必填 `target_users`、`core_scenarios`、`auth`、`mvp_features`；可选 `core_rules`、`non_goals`、`success_metrics` | 目标用户、核心场景、账号与权限、MVP 功能、核心业务规则（评分方式、状态流转等）、非目标、成功标准 | 阶段 A 的决策 |
| C 技术选型 | 必填 `frontend`、`backend`、`storage`、`deployment`；可选 `auth_impl`、`integrations` | 按层确定，选项附优缺点并标出推荐 | 规模默认值；已有仓库沿用识别到的技术栈 |
| D 实现方案 | 必填 `architecture`、`milestones`；可选 `modules`、`test_strategy`、`risks` | AI 给出 2–3 套具体方案，用户选择或修改 | 前三个阶段的决策 |

规模决定技术选型阶段的推荐项：

| 规模 | 默认推荐 |
| --- | --- |
| 本地工具 | 单机运行、SQLite、免登录、打包分发 |
| 开源项目 | 安装简单、许可证与文档、CI、可选的插件机制 |
| 在线部署 | 账号体系、PostgreSQL、容器化部署、监控告警 |
| 企业级 | SSO、多租户、审计日志、权限模型、合规与高可用 |

提问规则：

- 能从任务描述和已有决策推断的键直接写入账本（来源“AI 决定”），不再提问；用户随时可以改。
- 题型有单选、多选、自由填写。选项必须是贴合任务的具体内容（真实的技术名、功能、用户群），推荐项是 AI 自己会选的那个，描述里先写理由。自由填写题可以勾选“不确定，让 AI 填写”。
- 每轮最多 3 题，先问必填键，可选键每轮最多 1 题；每阶段最多 3 轮。账号与权限放在需求阶段，等目标用户明确后再问。
- “跳过剩余问题，进入下一阶段”：未答的题按推荐项处理，本阶段其余待定键由规划模型决定。
- 每条决策记录来源、理由和被否决的备选。
- 决策键声明依赖关系（例如 `storage` 依赖 `scale`）；回改后，依赖它的决策和文档小节标记“需复核”。
- 技术选型阶段可以查证（最多 3 次工具调用），没配搜索就标注“未查证”。实现：阶段 C 第一次出题前，路由模型给出最多 3 条搜索词，用第一个启用的搜索服务（博查 API、远程 MCP、本地 MCP）各搜一次，结果作为证据放进出题和代填的提示词，并存在该轮问题上显示来源；之后的轮次复用这份证据，不再搜索。搜索失败只记录，不阻断讨论。
- 已有仓库可以做一次只读扫描，识别出的技术栈预填阶段 C。实现：新建任务时选择文件夹，扫描最多 5000 个文件、6 层目录（跳过 `node_modules`、`.git`、构建产物等，不跟随符号链接），读取根目录附近的依赖清单（package.json、pyproject.toml、requirements.txt、go.mod、Cargo.toml、pom.xml、build.gradle、Gemfile、composer.json、docker-compose、schema.prisma）和标志性文件。识别出的层写成“AI 决定”的决策并注明来源文件，扫描摘要同时提供给分诊、出题、写文档和拆任务。

```json
{"key":"storage","value":"postgresql","stage":"tech","source":"recommended","rationale":"在线部署，多用户并发写入","alternatives":["sqlite","mysql"],"depends_on":["scale"],"needs_review":false}
```

## 文档产出

两份文档都从决策账本生成。快速通道不生成文档；轻量通道生成一份合并的精简版；完整通道生成 `PRD.md` 和 `TECH_DESIGN.md`。

| 文档 | 章节 |
| --- | --- |
| PRD.md | 背景与目标 · 项目定位与规模 · 目标用户与核心场景 · 功能需求（MVP / 后续） · 非功能需求 · 非目标 · 成功标准 · 待定问题 |
| TECH_DESIGN.md | 技术选型与理由（含放弃的备选） · 架构概览 · 模块划分 · 数据模型 · 接口 · 部署方案 · 安全与合规 · 测试策略 · 里程碑 · 风险 · 待确认问题 |

精简版的章节：目标 · 范围 · 实现思路 · 约束 · 验收标准 · 待定问题。

验收标准采用 EARS 句式，例如：“当用户提交空标题时，系统应当拒绝保存并提示标题必填。”

生成方式：

- 讨论结束（点“完成讨论，生成文档”或在最后一个阶段跳过剩余问题）后，该通道的文档同时开始生成，各自是一次规划模型的流式调用。
- 模型按固定顺序输出小节，每节以一行 `@@section:<id>` 开头；KM0 按标记切分，标题和编号由 KM0 统一加上。界面边收边显示已写完的小节。漏写的小节存为空，可以单独补写；一个标记都没有时报错并允许重试。
- 提示词要求：以决策账本为准，不擅自增加重大决策；不得不做的假设写进“待定问题”，一条一项列表；短段落、列表和表格，不写空话。
- 待定问题：文档页列出最新版本里的待定问题，用户可以一次写下答复（只答其中几条也行），KM0 用一次 AI 修订把答复写进相关小节、从待定问题里删去已回答的条目。拆任务前如果文档还有待定问题，任务页会提示任务将沿用文档里的假设。

版本与修订：

- 每次生成、手动编辑、AI 修订、恢复旧版本都产生新版本；旧版本只读，可以恢复为最新版本。
- 编辑和修订必须基于最新版本，否则提示冲突并刷新。
- AI 修订只替换指定的小节，其余小节原样保留；可以带一句修改要求，也可以不带（按当前决策重写）。
- 每个小节记录写作时所依据的决策值（章节模板里声明依据哪些决策键）。决策值变了，只有依据它的小节标记“已过期”，并给出变化的决策；“按新决策更新这些小节”一次重写所有过期小节。
- 手动编辑过的小节：整篇重新生成时可以选择保留；AI 重写它们之前先确认。
- 快速通道不写文档，讨论结束后直接进入任务拆解（P3）。

## 任务拆解与路由引擎

大模型只负责提取任务特征；难度由确定性规则计算，Agent 和模型由分发策略按能力先验、本地记录和成本选出，结果附理由，用户可以覆盖。

| 特征 | 取值 → 分值 |
| --- | --- |
| 影响范围 | 1 个文件 0 · 2～5 个 1 · 5 个以上 2 · 新子系统 3 |
| 需求模糊度 | 低 0 · 中 1 · 高 2 |
| 推理难度 | 照着做 0 · 需要判断 1 · 需要设计决策 3 |
| 上下文量 | 小 0 · 大 1 |
| 可验证性 | 有现成测试 0 · 没有 1 |
| 风险类型 | 无 · 数据迁移 · 安全 · 生产环境（走硬规则） |

总分 0～2 为 T1，3～5 为 T2，6 分及以上为 T3。硬规则：有风险类型 → 至少 T2；调试和修复 bug（任务类型 `fix`）→ 至少 T2；需要设计决策 → T3；纯文档或样板代码且不超过 5 个文件 → T1。这一档决定任务的难度段：T1 是“15 分钟以内”，T2 是“15 分钟–1 小时”，T3 是“1–4 小时”，8 分及以上是“4 小时以上”。每段的难度来自模型注册表（SWE-bench Verified 逐题结果的 Rasch 拟合），和模型能力在同一个尺度上。

分数和硬规则对应的单测在 `packages/core/src/routing/routing.test.ts`。总分达到 8 分或者“新建子系统”的任务标记“建议拆分”，搭项目骨架（boilerplate）除外。

- 拆解：规划模型读决策账本和该通道的文档（快速通道只有决策），一次结构化调用给出任务列表：标题、目标、EARS 验收标准（需求描述、决策和文档里写明的每条验收条件都要逐条落到对应任务的验收标准里，不能只留在引用的决策中；验收时 KM0 也把任务引用的决策交给评审模型一并核对）、涉及文件、依赖（只能依赖排在前面的任务，因此不会成环）、依据的决策键和文档小节，以及上表的特征。模型不选 Agent 和模型。
- 能力：任务需要什么能力（前端、后端、调试、测试、文档、部署与配置）由任务类型和涉及文件判断；判断不出时用综合能力。每个“Agent × 模型”组合的能力 = 模型在这项能力上的先验（注册表；不在注册表里的模型按自己的输出价格估计，没有价格时取很宽的分布）+ Agent 的修正（本家或非本家），再用本机的运行记录做贝叶斯更新（`packages/core/src/ability`）。首次通过概率 σ(θ + δ − d) 对三者的不确定度取 probit 近似。
- 候选与硬约束：候选是已启用的 Agent × 它在“设置 → Agent”里勾选的模型。接口格式不符的不算候选；上下文窗口小于任务需要（上下文少 32K、多 128K）、订阅额度已用完且设为“暂时不可用”的排除（额度用完但允许按 token 计费时改按官方价格计算；额度目前按 KM0 自己的调用统计）；有风险的任务要求即使按 10% 分位估计、通过率也不低于 50%，没有组合达到时选最有把握的并注明。
- 升级链：失败后换到预计通过率至少高 2 个百分点的组合，有同一 Agent 的就留在这个 Agent，其中单次成本最低的；最多三步，和 KM0 Runner 的阶梯一致。期望成本 = c₁ + (1 − p₁)(c₂ + (1 − p₂)c₃)。
- 选择：五档策略（激进、偏省、平衡、偏稳、保守，项目级设置、单个任务可以覆盖）各有首次通过率目标（50%–90%）和判断能力用的分位（均值到 10% 分位）。在达到目标的组合里选期望成本最低的；成本相差不到 2% 或一美分时，依次比通过率、是否擅长这项能力、是否本家、偏好顺序。没有组合达到目标时选最有把握的，并在汇总里提示。同一个模型的本家 Agent 与其他 Agent 预计通过率相差不到 5 个百分点时用本家。有风险的任务至少按“偏稳”。同样的输入下，档位越保守，期望成本不降；各组合不确定度相同时通过率也不降（单测覆盖）。
- 成本估算：按影响范围给出一次运行的 token 量（编码 Agent 每轮都会重读文件，输入远大于输出；上下文多、需求很模糊时上调），区间取中间值的 0.5～2 倍，乘以服务商计费后的单价（中转乘倍率，订阅内和免费为 0）。显示单次区间、沿升级链的期望成本，以及与“全部用最强组合”相比的节省；没有价格的任务不计入合计并单独提示。
- 预算：可以给项目设总预算。期望总成本超出时，列出改到更省的档位能省最多的任务，直到放进预算；放不进时说明。
- 理由：每个任务列出难度和策略、为什么选这个组合、没选更便宜组合的原因（低于目标、上下文不够、额度用完、风险下限、已失败、本家优先）、失败后的升级链，以及能力数据的来源（哪些榜单、截至哪天、本地记录几次）。
- 档位标签：T1/T2/T3 只用于显示和 KM0 Runner 的阶梯：按模型的综合能力在用户自己的模型里排在下、中、上三分之一，用户可以在模型上手动指定。
- 覆盖：策略档位和“Agent × 模型”组合都可以逐个任务手动覆盖，也可以恢复策略结果；手动指定的组合即使不满足硬约束也照用。所有结果在每次读取时重新计算，改了价格、模型、策略或记录立刻生效。
- 拆解之后文档又出了新版本时，提示任务可能过时；重新拆解会清除手动覆盖。
- 运行记录与升级：用户在任务详情里“记一次通过 / 记一次失败”（记下当时的组合），KM0 Runner 的验收结论也按每次尝试记录（最后一次在验收通过时算通过，用户改过的判定权重加倍）。记录按注册表模型存，同一个模型经过不同服务商共享记录，用来修正能力；“设置 → 模型”里每个模型显示本地记录次数和修正后的典型通过率，可以清除。同一组合失败 2 次（或 Runner 的工作被拒一次），任务排除这个组合和不比它强的组合，沿升级链往上；链走完就标记“需要你来决定”。升级后的交接包会告诉 Agent 上一次没通过、先检查遗留的改动。清除失败记录即恢复，也会删掉为这个任务手动记的结果；重新拆解会清空失败记录。
- 路由器自身分档：分诊和出题用路由模型，写文档和拆任务用规划模型。

## Agent 交接

第一期只生成和导出交接包，不替用户启动 Agent，也不写入目标仓库。

交接包是一个 zip，解压到目标代码库根目录后全部文件都在 `km0/` 文件夹里，不会覆盖代码库自己的文件：

```
km0/README.md          使用说明：任务表（档位、Agent、模型、启动命令）和各 Agent 的用法
km0/docs/PRD.md        最新版本的文档（轻量通道是 BRIEF.md，快速通道没有）
km0/docs/TECH_DESIGN.md
km0/tasks.json         机器可读的任务清单
km0/tasks/01.md …      每个任务一份自包含的说明
km0/agents/CLAUDE.md   各 Agent 的项目说明，按 README 放到对应位置；已有同名文件时合并
km0/agents/AGENTS.md
km0/agents/km0.mdc
```

每份任务说明包含：目标与 EARS 验收标准；可能涉及的文件；前置任务；任务引用的决策（附理由）；所引用文档小节的摘录；约束（范围、查证、决策和文档不一致时以文档为准、测试、按风险类型追加的注意事项）；完成后的自查要求；失败升级说明（整个任务升一档重做，不在中途换模型；T3 失败则交给人）。

上下文裁剪：只放任务引用的决策和小节；任务没有引用时，决策退回到交付形态和技术选型，小节退回到架构与模块（文档类任务退回到背景与功能需求）。每个小节最多 4000 字，整份摘录最多 12000 字，超出部分截断并指向完整文档。

启动命令统一让 Agent 自己读任务文件（“阅读 km0/tasks/01.md 并完成其中描述的任务”），避免在命令行里塞长文本，也不依赖具体的 shell。

### 模型注册表（正式版 R2）

`packages/registry` 每周从公开榜单（OpenRouter 及其附带的 Artificial Analysis、Design Arena 数据，Terminal-Bench，SWE-Bench Pro，SWE-rebench，SWE-bench，Aider）重新抓取成绩，对齐模型和 Agent 的名字，拟合每个模型在各类任务上的能力先验和每个 Agent 对本家模型、其他模型的修正，生成 `generated/model-registry.json`。注册表打进安装包和网页调试版，设置 → Agent → 模型能力数据里可以检查更新、从文件导入或恢复内置数据；下载或导入的版本存在 `model_registry` 表里，只有比内置的新时才使用。分发如何使用这些先验见 [ROADMAP-1.0.md](ROADMAP-1.0.md) 第 2、3 节。

### KM0 Runner 与验收（0.1.0 之后）

交接时可以选择交给 [KM0 Runner](https://github.com/WERvEX/KM0-runner)：它在独立的 git worktree 里逐个执行任务，卡住时沿阶梯换更强的模型，交回分支和执行报告。KM0 导入一次运行（`runs/<run_id>` 文件夹），用规划模型对照每个任务的 EARS 验收标准判定，评审同时看到原始需求、任务引用的决策和上游任务的改动；判定可以手动改。每次尝试都记为运行记录；未通过的任务排除 Runner 最后用的模型，换到更强的组合重新分发。判定写回 `acceptance.jsonl`，Runner 用它校准路由规则，校准结果在“设置 → Agent”里导入。

### 从 KM0 执行（正式版 R5）

路由表下方的“执行”面板一键执行，执行方式在“设置 → 执行”里选：

- **KM0 Runner（默认）**：自动在 PATH 里找 `km0-runner`，或 `python -m km0_runner`，也可以手填启动方式；版本低于 0.3.0 时提示升级。pi 需要是 Runner 锁定的 1.3.0。运行目录默认是数据文件夹下的 `runs/`。
- **Runner 配置**：默认由 KM0 生成——每个分到模型的任务带自己的阶梯（`task_ladders`）：分到的组合，再加上它的升级链；每一级用档位标签命名，同一条链里标签重复时加后缀（如 `T2-2`），已在阶梯上的模型不重复。整次运行的阶梯只给没分到模型的任务用，每一档取路由结果里这个档位标签最常用的模型（没有时取升级链上的）。pi 的 `models.json` 取自“设置 → 模型”的服务商和价格，`apiKey` 写成 `$KM0_KEY_<服务商>`，密钥只通过环境变量交给子进程，不写进文件。也可以改用自己的 `runner.yaml`。
- **自定义命令（未验证）**：命令模板里的 `{package}`、`{repo}`、`{run_dir}`、`{tasks}` 会被替换，用系统 shell 执行。KM0 只负责启动、显示输出和停止；结束后运行目录里有 Runner 格式的结果就导入，没有就提示手动导入。
- **执行前检查**：逐项列出仓库（必须是 git 仓库；没关联时可以当场选择）、Runner、pi、阶梯、服务商密钥和预算，不通过的项给出去哪里修改，有阻塞项时不能开始。
- **执行中**：KM0 写出交接包（`<runs>/<run_id>.km0/`）和配置，启动 `km0-runner run … --runs <runs> --run-id <run_id>`，每 0.5 秒跟读运行目录里的 `progress.jsonl`，面板显示每个任务的状态、档位与模型、升档记录、花费与预算和最近的输出。KM0 重启后从这个文件恢复状态，没有结束的执行标为“已中断”。
- **停止**：在运行目录写 `STOP`（Windows 也适用），POSIX 上同时发 SIGTERM；Runner 停下 pi，提交当前任务已有的改动，把剩下的任务标为已取消。关闭窗口时如果还有执行，先用应用内对话框询问，确认后停止再退出。
- **结束后**：自动导入运行结果并验收，结束用应用内提示告知；没通过的任务可以“从更强的组合重做”（`--tasks … --reuse <run_id>`，验收被拒的任务已沿升级链往上）。

网页调试版不能启动本地程序，执行入口显示为不可用并说明原因。

### 直接交给 Agent（1.1）

第三种执行方式。KM0 只负责规划每个任务由哪个 Agent 的哪个模型来做，然后把任务原样交给它；执行中不切换模型（Runner 仍然按自己的规则切换）。目前能直接交付的 Agent 是 Claude Code 和 Claude Desktop（`DIRECT_AGENTS`），其他 Agent 的任务在预检里列出、阻止开始。

- **执行过程**（`apps/desktop/src/main/dispatch/direct-run.ts`，在主进程里运行）：
  1. 按依赖顺序，给每个任务在运行目录下建 worktree，分支 `km0/<run_id>/<NN>`。有依赖的任务从第一个上游分支开始，再依次合并其他上游分支，冲突就标为“阻塞”。
  2. 把交接包的 `km0/` 复制进 worktree，交给 Agent。
  3. Agent 结束后，把剩下的改动（不含 `km0/`）提交到任务分支，有测试命令就运行。
  4. 写报告（`report_version: 2`，多一个 `agent` 字段，`attempts[].agent` 也记下），然后删掉 worktree，保留分支。

  运行目录里的 `progress.jsonl`、`reports/`、`diffs/`、`summary.json`、`STOP` 和退出码（0、1、3）都和 KM0 Runner 一样，所以面板、停止、导入、验收、本地记录和重做都不用区分执行方式。新增的进度事件是 `task_waiting`（等待领取）和 `task_claimed`。
- **Claude Code**（`dispatch/claude-code.ts`）：
  - 命令：`claude -p --output-format stream-json --verbose --permission-mode acceptEdits --model <模型> [--max-budget-usd <剩余预算>] --allowedTools …`，提示词从 stdin 传入。
  - 读输出：每次工具调用算一步，并写进“最近的输出”；`result` 事件给出花费、token 用量和是否出错。
  - 停止：结束整个进程组，Windows 上用 `taskkill /T`。
  - 登录：服务商有 Key 或地址时，通过 `ANTHROPIC_API_KEY`、`ANTHROPIC_BASE_URL` 传入；没有时用 Claude Code 自己的登录，设置页提示用户自行确认订阅条款。
- **Claude Desktop**：预置 Agent，默认不启用，能用的模型和 Claude Code 一样，由用户在路由表里手动指定。
  - 执行到它的任务时，KM0 在数据文件夹的 `dispatch/` 里写一个任务文件（`dispatch/inbox.ts`）并等待回报。
  - Claude Desktop 通过 KM0 的 MCP 服务器（`src/mcp/server.ts`）调用 `km0_next_task` 领取任务，用 `km0_list_files`、`km0_read_file`、`km0_write_file`、`km0_delete_file` 修改，用 `km0_run_tests` 跑测试，最后 `km0_report`。
  - 这些文件工具只能访问任务的 worktree：不能用 `..` 跳出，不能碰 `.git`，符号链接按真实路径检查。
  - MCP 服务器是一个独立的脚本（esbuild 打包成 `out/mcp/km0-mcp.cjs`，安装包里放在 asar 之外的 `resources/km0-mcp.cjs`），由 KM0 自己的可执行文件以 `ELECTRON_RUN_AS_NODE=1` 运行；它不碰数据库，只读写 `dispatch/`。“设置 → 执行”给出要加进 `claude_desktop_config.json` 的片段，以及交互式 Claude Code 用的 `claude mcp add` 命令。
- **测试**：
  - `e2e/fixtures/fake-claude.mjs` 冒充 `claude`；单测和 e2e 里由脚本化的 MCP 客户端扮演 Claude Desktop。e2e 用设置页给出的片段原样启动 MCP 服务器。
  - `KM0_CLAUDE_REAL=1` 时用真实的 `claude` 跑一个小任务。
  - 真实环境的手动验收见 [checklists/claude-agents.md](checklists/claude-agents.md)。

### 更新、备份与评测（正式版 R6）

- **应用内更新**：electron-updater 读 GitHub Releases（`electron-builder.yml` 的 `publish`）。启动 8 秒后按偏好检查一次；下载和重启都由用户在“设置 → 关于”里点，进度和说明都在页面里，有执行没结束时重启前同样先询问。开发版、网页调试版、非 AppImage 的 Linux 安装和未签名的 macOS 版本不更新，并说明原因。环境变量 `KM0_UPDATE_FEED` 把更新源换成一个 generic feed，“关于”页会显示这个来源。`pnpm e2e:update` 用这个变量真实测试一次更新：先打包 9.9.1 和 9.9.2 两个版本（`pnpm e2e:update:build`），装上 9.9.1，用本地 HTTP 服务器提供 9.9.2，在“关于”里检查、下载、重启安装，再启动确认版本已变、数据还在。CI 的 `update-test` 在 Linux（AppImage）和 Windows（NSIS）上跑这个测试。
- **签名**：CI 有证书密钥时签名 Windows 安装包、签名并公证 macOS 应用（hardened runtime，`build/entitlements.mac.plist`），没有时照常发布未签名版并在发布说明末尾写明。
- **数据库备份**：有待执行的迁移时，先用 `VACUUM INTO` 把数据库复制成 `km0.db.before-<n>-<时间>.bak`，保留最近 3 份。
- **离线评测**：`packages/eval` 检查拆解是否保留了需求里写明的每条验收条件，以及验收评审和隐藏测试是否一致。模型回答按 prompt 录制，回放不需要 API Key；prompt 改了就要重新录制，所以评测手动运行，不进 CI（CI 只跑它自己的单测）。

## 系统架构与技术栈

KM0 是桌面应用：Electron + TypeScript 全栈，不起本地 Web 服务，不用 Agent 框架。界面进程和主进程通过类型化 IPC 通信；核心逻辑是不依赖 Electron 的纯 TypeScript 包；每个用户操作对应一次 IPC 调用、最多一次大模型调用。

- 大模型调用：OpenAI SDK（覆盖 OpenAI 及所有兼容接口）+ Anthropic SDK，外包一层自写网关。每类输出一个 zod schema；结构化输出方式按模型配置选择（原生 JSON Schema / 工具调用 / 提示词加解析），连接测试时自动探测；校验失败修复重试一次，仍失败就报错；每次调用记录 token、成本和耗时。
- 讨论流程是自写的状态机（类型化状态 + 迁移表 + 每阶段一个函数）。
- 并发：每个项目同一时间只处理一个请求；提交回答必须带当前轮次 id。
- 错误分类：配置错误提示去设置；上游错误可重试；校验错误退回当前步骤。
- 安全：窗口开启 contextIsolation 和 sandbox，关闭 nodeIntegration，打包版设置严格 CSP；预加载脚本只暴露契约里的调用；网络请求和大模型调用都在主进程；应用单实例运行。

| 层 | 选择 |
| --- | --- |
| 桌面外壳与打包 | Electron + electron-vite + electron-builder |
| 语言与仓库 | TypeScript（严格模式、ESM），pnpm workspaces |
| 界面 | React + Vite，Tailwind CSS，Radix 组件，lucide 图标 |
| 界面数据与路由 | TanStack Query（封装 IPC）、TanStack Router（hash 模式） |
| 表单 | React Hook Form + zod |
| 中英文 | i18next + react-i18next |
| IPC 与校验 | 自定义类型化契约，zod 4 |
| 模型调用 | OpenAI SDK + Anthropic SDK + 自写网关 |
| 数据库 | Electron 内置的 `node:sqlite`（无原生模块），手写 SQL 迁移，WAL 模式 |
| 密钥 | Electron safeStorage；无密钥环时降级为混淆并在“关于”页提示 |
| 测试 | Vitest + Testing Library；Playwright 驱动 Electron 做端到端 |
| 检查与 CI | Biome + tsc；GitHub Actions 三平台构建 |

数据库没有采用最初规划的 Drizzle：Drizzle 正式版尚不支持 `node:sqlite`，而改用 `node:sqlite` 可以完全避免原生模块，三平台打包更简单。

### 网页调试版

为了不必每次下载安装包，同一套界面和服务还能构建成纯静态网页（`pnpm web:build`，CI 部署到 GitHub Pages 的 `gh-pages` 分支）：

- 服务层只依赖一个很小的同步 `Database` 接口（`src/main/db/sql.ts`）。桌面版用 `node:sqlite` 实现；网页版用 sql.js（WebAssembly 版 SQLite）实现，整个库文件存在 IndexedDB，改动后延迟约 300 ms 写回，页面隐藏时立即写回。迁移和业务代码两边完全相同。
- 网页入口（`src/web`）在页面内创建 `SettingsStore`、`ProjectService` 和同一个分发器，赋值给 `window.km0`，界面代码不需要区分环境。
- 模型调用直接从浏览器发出（SDK 开启 `dangerouslyAllowBrowser`）；Anthropic、OpenAI、DeepSeek、Qwen、GLM 的接口都允许跨域请求。
- 密钥只做混淆，页面顶部常驻提示。`?simulated=1` 切换到模拟模型，模拟数据和真实数据分库保存。
- 它只用于调试，不是正式交付形态。

```
km0/
├─ packages/core     领域逻辑与模型网关（纯 TS）
├─ packages/shared   zod schema、IPC 契约、共享类型
├─ packages/registry 模型注册表：抓取榜单、对齐名字、拟合能力先验（见其 README）
├─ apps/desktop
│  ├─ src/main       主进程：数据库、设置、IPC 处理
│  ├─ src/preload    只暴露契约里定义的 API
│  └─ src/renderer   React 界面
└─ e2e/              Playwright 端到端测试
```

## 数据模型与 IPC 接口

数据库是应用数据目录（Windows 下为 `%APPDATA%\KM0`）里的一个 SQLite 文件，迁移只追加、不修改已发布的迁移。

| 表 | 说明 |
| --- | --- |
| `projects` | 一次任务就是一个项目：标题、描述、通道、阶段、仓库路径、分发策略档位、预算 |
| `question_rounds` | 每轮问题与回答，提交时校验轮次 |
| `decisions` | 决策账本：值、来源、理由、备选、依赖、是否需复核 |
| `documents` | PRD、技术方案、精简版的各个版本；每版存渲染好的 Markdown 和各小节（正文、是否手动编辑、写作时依据的决策值） |
| `tasks` | 任务、特征、依赖、人工覆盖（策略档位、Agent × 模型）、失败记录（组合与档位标签；难度、Agent、模型、成本读取时计算） |
| `routing_plans` | 每个项目最近一次拆解所依据的文档版本 |
| `handoffs` | 生成过的交接包：任务、Agent、文件清单 |
| `providers` | 服务商：接口格式、地址、密钥（加密）、计费方式（按 token / 中转倍率 / 订阅 / 免费） |
| `models` | 服务商下的模型：模型 ID、显示名称、手动指定的榜单模型、上下文窗口、价格覆盖、结构化输出方式、手动指定的档位标签；KM0 的路由 / 规划角色和 Agent 都从这里选 |
| `agents` | 预设和自定义 Agent：启用、偏好、擅长的能力；自定义 Agent 还有项目说明文件、启动命令模板、能接的接口格式和本家厂商 |
| `agent_models` | 每个 Agent 能用哪些模型 |
| `runs` | KM0 启动的执行：执行方式、状态、运行目录、只重做的任务和所基于的运行、退出码、错误、花费、最后几行输出、导入后的 Runner 运行 |
| `run_records` | 本机的运行记录：注册表模型、Agent、是否本家、能力类别、难度段、是否通过、权重、来源（手动 / 验收），只在本机，用来修正能力先验 |
| `model_registry` | 下载或导入的模型注册表（比内置的新时才使用） |
| `llm_calls` | 调用日志：用途、token、成本、耗时、错误 |
| `search_services`、`preferences` | 查证搜索服务（密钥加密）；界面偏好与角色分配 |

`question_rounds.research_json` 保存技术选型轮次的查证结果，`projects.repo_scan_json` 保存仓库扫描结果。

IPC 通道定义在 `packages/shared/src/ipc.ts`，主进程按 zod schema 校验参数后再调用处理函数。主进程向界面推送的事件（目前只有文档生成进度）走单独的 `km0:event` 通道，约每 80 ms 合并一次：

| 通道 | 用途 |
| --- | --- |
| `project.*` | 提交任务并分诊、读取项目全貌、改通道、重命名、删除 |
| `round.answer` / `stage.advance` | 提交本轮回答；进入下一阶段 |
| `decision.update` | 回改决策，返回需复核的内容 |
| `document.*` | 读取某个版本、生成（流式，进度通过 `document.progress` 事件推送）、保存小节、按小节修订、恢复旧版本 |
| `routing.*` / `task.override` | 读取路由结果；拆任务并路由；设置项目的策略档位和预算；覆盖或恢复某个任务的策略档位和组合 |
| `task.record` / `task.clearFailures` | 记一次通过或失败（同一组合失败 2 次沿升级链往上）；清除失败记录 |
| `handoff.build` | 按当前路由生成交接包（zip 在界面里打包，用 `files.save` 保存） |
| `execution.*` | 执行方式的设置；检测 Runner 和 pi；执行前检查；开始、停止、列出执行（进度通过 `execution.update` 事件推送） |
| `update.*` | 应用内更新：状态、检查、下载、重启安装（状态通过 `update.state` 事件推送） |
| `project.setRepo` / `app.quit` | 给已有项目关联仓库；关闭窗口时停止还在进行的执行并退出 |
| `settings.*` | 服务商与模型（含连接测试、按名字搜索榜单模型、清除本地记录）、角色、Agent 启用与排序、能用的模型、自定义 Agent、搜索服务与测试、偏好、配置导入导出（v2 格式，仍能读 0.1 的 v1 文件） |
| `registry.*` | 模型注册表的信息、更新、导入、恢复内置数据、厂商列表 |
| `repo.pick` / `repo.scan` | 选择文件夹；只读扫描本地仓库 |
| `files.*` / `folder.answer` | 桌面版 KM0 自己的文件浏览器：列目录、读取导入的文件、保存导出的文件、在文件夹中显示；回答主进程发来的 `folder.request` |

主进程推送的事件还有 `execution.update`（执行的进度和结果）、`app.quitRequest`（关闭窗口时还有执行，请界面询问）、`folder.request`（服务需要用户选文件夹时，请界面打开文件浏览器）和 `app.notice`（主进程的错误、界面崩溃后自动重新加载等，在界面里用提示条显示）。

## 界面设计

三栏布局：左栏是项目列表；中间工作区按阶段切换（分诊卡、阶段进度与问题卡、文档页、路由表、交接面板）；右栏是决策账本。设置页包含模型与角色、Agent（含模型目录）、搜索服务、通用（含配置导入导出）、关于。

窗口宽度不足 1280 像素时，决策账本收进页头的“决策账本”按钮，点开后从右侧滑出，中间的工作区保持够用的宽度。

界面规范（正式版 R0，见 [ROADMAP-1.0.md](ROADMAP-1.0.md) 第 5 节）：

- 不弹系统或浏览器的对话框。确认用 `ConfirmDialog`，消息用提示条（`useToast`），选文件夹、导入和保存文件用 KM0 自己的文件浏览器（`useFiles`）。主进程需要文件夹时发 `folder.request`，未捕获的异常只写日志并发 `app.notice`，不让 Electron 弹出错误框；真有下载发生时直接存进“下载”文件夹，不弹保存框。
- 网页调试版没有别的办法读写本地文件，只在 `lib/browser-files.ts` 和 `web/*-access.ts` 里用浏览器自带的文件选择和下载，这是仅有的例外。
- `pnpm lint` 里的 `scripts/check-ui-rules.mjs` 拦截 `alert`、`confirm`、`prompt`、Electron `dialog`、系统通知、离开页面提示和例外文件之外的浏览器文件选择；端到端测试把 Electron 的 `dialog` 换成一调用就失败的桩，页面出现原生弹窗也算失败。
- `e2e/ui.spec.ts` 在两种窗口、两种语言、两种主题下逐个打开主要界面，检查布局（横向滚动、文字截断、按钮折行、多余的滚动条）和 axe 可访问性（含对比度），并把截图集写到 `test-results/ui/`。颜色令牌按 WCAG AA 设定，在面板和 15% 的同色底上都不低于 4.5:1。

配置导入导出：导出为一个 `km0-config` JSON 文件，包含模型配置、角色（按名称引用）、Agent 启用顺序、擅长的能力与模型目录、搜索服务和界面偏好；默认不含密钥，勾选后以明文写入。导入按名称合并，已有的更新、没有的新建，不删除任何配置，文件里没有密钥时保留本机已存的密钥。

## 风险

| 风险 | 应对 |
| --- | --- |
| Pi、DSH、ZCode、Cursor 的接口查不到或不稳定 | 降级为通用提示词 + 使用说明；适配器独立文件 |
| 打分规则初值不准 | 阈值可配置；失败升级兜底；第二期用执行结果校准 |
| 便宜的路由模型出题质量不够 | 问题绑定决策键，由模板约束必问内容；可切换为规划模型 |
| 文档过长 | 固定章节，只写决策和必要说明；交接包只给相关小节 |
| 开发开始后文档过时 | 第一期靠版本和复核；第二期做执行状态回写 |
| `node:sqlite` 在 Node 24 仍为候选稳定级 | 数据访问集中在主进程的仓储层，必要时可替换驱动 |
